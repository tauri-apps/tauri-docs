---
title: Проблемы графики в Linux
---

В Linux Tauri рендерит через WebKitGTK. В некоторых системах, чаще всего с GPU NVIDIA, WebKitGTK и графический драйвер не согласуются, и вы получаете всё — от пустого окна до едва заметных проблем с рендерингом. На этой странице собраны известные симптомы и способы обхода. См. [tauri-apps/tauri#9394](https://github.com/tauri-apps/tauri/issues/9394) для оригинальных сообщений.

## Распространённые симптомы

- Окно открывается, но остаётся пустым или белым.
- Окно мерцает, особенно при изменении размера.
- Приложение падает при изменении размера без полезного вывода ошибок.
- Консоль показывает `AcceleratedSurfaceDMABuf was unable to construct a complete framebuffer`.
- Консоль показывает `Gdk-Message: Error 71 (Protocol error) dispatching to Wayland display.`

Большинство из них связано с тем, что рендерер DMABUF в WebKitGTK запрашивает форматы буферов, которые драйвер NVIDIA не предоставляет. См. [трекер ошибок WebKitGTK](https://bugs.webkit.org/show_bug.cgi?id=261874) и [форумы NVIDIA](https://forums.developer.nvidia.com/t/geforce-rtx-4070-flickering-issue-when-using-the-dmabuf-renderer-in-webkitgtk/274741) для обсуждения вышестоящих проектов.

## Способы обхода

Пробуйте их по порядку. Более ранние сохраняют аппаратное ускорение.

1. Убедитесь, что включён kernel mode setting. Драйверам NVIDIA старше 545 часто требуется `nvidia_drm.modeset=1` в качестве параметра ядра.
2. Установите `__NV_DISABLE_EXPLICIT_SYNC=1`. Это часто устраняет падение Wayland с `Error 71` без потери производительности.
3. Установите `WEBKIT_DISABLE_DMABUF_RENDERER=1`. Устраняет ошибку кадрового буфера DMABUF и падение с `Error 71`, ценой отказа от более быстрого пути рендеринга.
4. Установите `WEBKIT_DISABLE_COMPOSITING_MODE=1`. Крайняя мера для тихого падения при изменении размера. Полностью отключает аппаратное композитирование.

Вы можете установить эти переменные в своём shell для проверки или задать их в `main()` до создания webview, чтобы пользователям не приходилось делать это самостоятельно:

```rust
fn main() {
  // Workaround for WebKitGTK on NVIDIA, see tauri-apps/tauri#9394
  #[cfg(target_os = "linux")]
  std::env::set_var("WEBKIT_DISABLE_DMABUF_RENDERER", "1");

  tauri::Builder::default()
    // ...
}
```

Отправляйте безусловное переопределение, подобное этому, только если вы подтвердили, что ваше приложение подвержено проблеме. Оно отключает более быстрый путь для всех, включая пользователей с рабочими конфигурациями.

## Тихие сбои: WebGL и canvas

Не каждая проблема приводит к падению или ошибке. Контент WebGL и canvas может тихо перейти на медленный путь, пока остальная часть приложения выглядит нормально. Две вещи затрудняют обнаружение этого изнутри вашего фронтенда:

- Создание контекста WebGL2 успешно даже тогда, когда результат обеспечивается программным растеризатором или медленным путём отображения. Не существует ошибки, которую можно перехватить.
- WebKitGTK маскирует строку рендерера WebGL для защиты от фингерпринтинга. `WEBGL_debug_renderer_info` сообщает `Apple GPU` на каждой машине с Linux, поэтому вы не можете проверить, что на самом деле стоит за контекстом.

На практике это проявляется как высокая задержка ввода или низкая частота кадров в представлениях с интенсивным использованием WebGL (эмуляторы терминала, редакторы, карты, графики), при этом тот же код быстр в обычном браузере. Если ваше приложение имеет путь рендеринга через WebGL, дайте ему запасной вариант без WebGL на Linux и рассмотрите возможность добавления настройки, чтобы пользователи могли переключаться, вместо того чтобы полагаться на информацию от контекста.
