Ce guide vous explique comment mettre à niveau votre application basée sur Tauri 1.0 vers Tauri 2.0.

## Préparer le mobile

L'interface mobile de Tauri nécessite que votre projet produise une bibliothèque partagée. Si vous ciblez le mobile pour votre application existante, vous devez modifier votre crate pour produire ce type d'artefact en plus de l'exécutable desktop.

1. Modifiez le manifeste Cargo pour produire la bibliothèque. Ajoutez le bloc suivant :

```toml
// src-tauri/Cargo.toml
[lib]
name = "app_lib"
crate-type = ["staticlib", "cdylib", "rlib"]
```

2. Renommez `src-tauri/src/main.rs` en `src-tauri/src/lib.rs`. Ce fichier sera partagé par les cibles desktop et mobiles.

3. Renommez l'en-tête de la fonction `main` dans `lib.rs` comme suit :

```rust
// src-tauri/src/lib.rs
#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    // your code here
}
```

La macro `tauri::mobile_entry_point` prépare votre fonction pour son exécution sur mobile.

4. Recréez le fichier `main.rs` qui appelle la fonction `run` partagée :

```rust
// src-tauri/src/main.rs
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]

fn main() {
  app_lib::run();
}
```

## Migration automatisée

:::danger

Cette commande ne remplace pas ce guide. Lisez la page _entière_ même si vous choisissez d'utiliser la commande.

:::

La CLI Tauri v2 inclut une commande `migrate` qui automatise la majeure partie du processus et vous aide à terminer la migration :

<CommandTabs
  npm="npm install @tauri-apps/cli@latest
    npm run tauri migrate"
  yarn="yarn upgrade @tauri-apps/cli@latest
    yarn tauri migrate"
  pnpm="pnpm update @tauri-apps/cli@latest
    pnpm tauri migrate"
  cargo='cargo install tauri-cli --version "^2.0.0" --locked
    cargo tauri migrate'
/>

Apprenez-en plus à propos de la commande `migrate` dans la [référence de l'interface en ligne de commande](/reference/cli/#migrate)

## Résumé des changements

Voici ci-dessous un résumé des changements entre Tauri 1.0 et Tauri 2.0 :

### Configuration Tauri

- `package > productName` et `package > version` ont été déplacés vers l'objet de premier niveau.
- le nom du binaire n'est plus automatiquement renommé pour correspondre à `productName`, vous devez donc ajouter une chaîne `mainBinaryName` à l'objet de premier niveau qui correspond à `productName`.
- `package` a été supprimé.
- la clé `tauri` a été renommée en `app`.
- `tauri > allowlist` a été supprimé. Consultez [Migrer les permissions](#migrate-permissions).
- `tauri > allowlist > protocol > assetScope` a été déplacé vers `app > security > assetProtocol > scope`. Consultez [Portée du protocole asset](/security/asset-protocol/) pour `enable`, les motifs glob, `requireLiteralLeadingDot` et les chemins dynamiques.
- `tauri > cli` déplacé vers `plugins > cli`.
- `tauri > windows > fileDropEnabled` renommé en `app > windows > dragDropEnabled`.
- `tauri > updater > active` retiré.
- `tauri > updater > dialog` retiré.
- `tauri > updater` déplacé vers `plugins > updater`.
- `bundle > createUpdaterArtifacts` ajouté, et doit être défini lorsque vous utilisez le système de mise à jour de l'app.
  - définissez-le sur `v1Compatible` lors de la mise à niveau d'apps v1 déjà distribuées. Consultez le [guide du plugin updater](/plugin/updater/) pour plus d'informations.
- `tauri > systemTray` renommé en `app > trayIcon`.
- `tauri > pattern` déplacé vers `app > security > pattern`.
- `tauri > bundle` déplacé au niveau supérieur.
- `tauri > bundle > identifier` déplacé vers l'objet de premier niveau.
- `tauri > bundle > dmg` déplacé vers `bundle > macOS > dmg`
- `tauri > bundle > deb` déplacé vers `bundle > linux > deb`
- `tauri > bundle > appimage` déplacé vers `bundle > linux > appimage`
- `tauri > bundle > macOS > license` retiré, utilisez `bundle > licenseFile` à la place.
- `tauri > bundle > windows > wix > license` retiré, utilisez `bundle > licenseFile` à la place.
- `tauri > bundle > windows > nsis > license` retiré, utilisez `bundle > licenseFile` à la place.
- `tauri > bundle > windows > webviewFixedRuntimePath` retiré, utilisez `bundle > windows > webviewInstallMode` à la place.
- `build > withGlobalTauri` déplacé vers `app > withGlobalTauri`.
- `build > distDir` renommé en `frontendDist`.
- `build > devPath` renommé en `devUrl`.

[Référence de l'API de configuration de Tauri 2.0](/reference/config/)

### Nouvelles Fonctionnalités de Cargo

- linux-protocol-body: Permet les protocols de requêtes "body parsing", autorisant l'IPC à l'utiliser. Nécéssite webkit2gtk 2.40.

### Fonctionnalités Cargo Retirées

- reqwest-client: reqwest est maintenant le seul client supporté.
- reqwest-native-tls-vendored: utilisez `native-tls-vendored` à la place.
- process-command-api: utilisez le plugin `shell` à la place (voir les instructions dans la section suivante).
- shell-open-api: utilisez le plugin `shell` à la place (voir les instructions dans la section suivante).
- windows7-compat: déplacé vers le plugin `notification`.
- updater: Updater est maintenant un plugin.
- linux-protocol-headers: est maintenant activé par défaut car la version minimal de webkit2gtk a été augmentée.
- system-tray: renomé en `tray-icon`.

### Changement de Crate Rust

- `api` module enlevé. Chaque module d'API peut être trouvé dans un plugin Tauri.
- `api::dialog` module enlevé. Utilisez `tauri-plugin-dialog` à la place. [Migration](#migrer-vers-un-dialog-plugin)
- `api::file` module enlevé. Utilisez Rust's [`std::fs`](https://doc.rust-lang.org/std/fs/) à la place.
- `api::http` module enlevé. Utilisez `tauri-plugin-http` à la place. [Migration](#migrer-vers-un-plugin-http)
- `api::ip` module réécrit et déplacé vers `tauri::ipc`. Jetez un œil aux nouvelles APIs, particulièrement `tauri::ipc::Channel`.
- fonctions du module `api::path` et `tauri::PathResolved` déplacées vers `tauri::Manager::path`. [Migration](#migrer-de-path-vers-tauri-manager)
- `api::process::Command`, `tauri::api::shell` et `tauri::Manager::shell_scope` APIs enlevées. Utilisez `tauri-plugin-shell` à la place. [Migration](#migrer-vers-un-shell-plugin)
- `api::process::current_binary` et `tauri::api::process::restart` déplacés vers `tauri::process`.
- `api::version` module a été retiré. Utilisez la [crate semver](https://docs.rs/semver/latest/semver/) à la place.
- `App::clipboard_manager` et `AppHandle::clipboard_manager` enlevés. Utilisez `tauri-plugin-clipboard` à la place. [Migration](#migrer-vers-un-clipboard-plugin)
- `App::get_cli_matches` enlevé. Utilisez `tauri-plugin-cli` à la place. [Migration](#migrer-vers-un-cli-plugin)
- `App::global_shortcut_manager` et `AppHandle::global_shortcut_manager` enlevés. Utilisez `tauri-plugin-global-shortcut` à la place. [Migration](#migrer-vers-un-global-shortcut-plugin)
- `Manager::fs_scope` enlevé. Le "scope" du fichier système est accessible via `tauri_plugin_fs::FsExt`.
- `Plugin::PluginApi` reçoit maintenant une configuration de plugin en tant que deuxième argument.
- `Plugin::setup_with_config` enlevé. Utilisez `tauri::Plugin::PluginApi` mis à jour à la place.
- `scope::ipc::RemoteDomainAccessScope::enable_tauri_api` et `scope::ipc::RemoteDomainAccessScope::enables_tauri_api` enlevés. Activer chaque plugin "core" individuellement via `scope::ipc::RemoteDomainAccessScope::add_plugin` à la place.
- `scope::IpcScope` retiré, utilisez `scope::ipc::Scope` à la place.
- `scope::FsScope`, `scope::GlobPattern` et `scope::FsScopeEvent` retirés, utilisez respectivement `scope::fs::Scope`, `scope::fs::Pattern` et `scope::fs::Event`.
- `updater` module enlevé. Utilisez `tauri-plugin-updater` à la place. [Migration](#migrer-vers-un-updater-plugin)
- Le champ `Env.args` a été supprimé, utilisez le champ `Env.args_os` à la place.
- `Menu`, `MenuEvent`, `CustomMenuItem`, `Submenu`, `WindowMenuEvent`, `MenuItem` et `Builder::on_menu_event` APIs enlevés. [Migration](#migrer-vers-un-menu)
- `SystemTray`, `SystemTrayHandle`, `SystemTrayMenu`, `SystemTrayMenuItemHandle`, `SystemTraySubmenu`, `MenuEntry` et `SystemTrayMenuItem` APIs enlevées. [Migration](#migrer-vers-un-tray-icon-module)

### Changements de l'API JavaScript

Le package `@tauri-apps/api` ne fournit plus de modules non core. Seuls les anciens modules `tauri` (maintenant `core`), `path`, `event` et `window` sont exportés. Tous les autres ont été déplacés vers des plugins.

- `@tauri-apps/api/tauri` module renommé en `@tauri-apps/api/core`. [Migration](#migrate-to-core-module)
- `@tauri-apps/api/cli` module enlevé. Utilisez `@tauri-apps/plugin-cli` à la place. [Migration](#migrer-vers-un-cli-plugin)
- `@tauri-apps/api/clipboard` module enlevé. Utilisez `@tauri-apps/plugin-clipboard` à la place. [Migration](#migrer-vers-un-clipboard-plugin)
- `@tauri-apps/api/dialog` module enlevé. Utilisez `@tauri-apps/plugin-dialog` à la place. [Migration](#migrer-vers-un-dialog-plugin)
- `@tauri-apps/api/fs` module enlevé. Utilisez `@tauri-apps/plugin-fs` à la place. [Migration](#migrer-vers-un-file-system-plugin)
- `@tauri-apps/api/global-shortcut` module enlevé. Utilisez `@tauri-apps/plugin-global-shortcut` à la place. [Migration](#migrer-vers-un-global-shortcut-plugin)
- `@tauri-apps/api/http` module enlevé. Utilisez `@tauri-apps/plugin-http` à la place. [Migration](#migrer-vers-un-plugin-http)
- `@tauri-apps/api/os` module enlevé. Utilisez `@tauri-apps/plugin-os` à la place. [Migration](#migrer-vers-un-os-plugin)
- `@tauri-apps/api/notification` module enlevé. Utilisez `@tauri-apps/plugin-notification` à la place. [Migration](#migrer-vers-un-notification-plugin)
- `@tauri-apps/api/process` module enlevé. Utilisez `@tauri-apps/plugin-process` à la place. [Migration](#migrer-vers-un-process-plugin)
- `@tauri-apps/api/shell` module enlevé. Utilisez `@tauri-apps/plugin-shell` à la place. [Migration](#migrer-vers-un-shell-plugin)
- `@tauri-apps/api/updater` module enlevé. Utilisez `@tauri-apps/plugin-updater` à la place [Migration](#migrer-vers-un-updater-plugin)
- `@tauri-apps/api/window` module renommé en `@tauri-apps/api/webviewWindow`. [Migration](#migrate-to-new-window-api)

Les plugins v1 sont maintenant publiés sous la forme `@tauri-apps/plugin-<nom-du-plugin>`. Auparavant, ils étaient disponibles depuis git sous la forme `tauri-plugin-<nom-du-plugin>-api`.

### Changements des variables d'environnement

La plupart des variables d'environnement lues et écrites par la CLI Tauri ont été renommées pour plus de cohérence et pour éviter les erreurs :

- `TAURI_PRIVATE_KEY` -> `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_KEY_PASSWORD` -> `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
- `TAURI_SKIP_DEVSERVER_CHECK` -> `TAURI_CLI_NO_DEV_SERVER_WAIT`
- `TAURI_DEV_SERVER_PORT` -> `TAURI_CLI_PORT`
- `TAURI_PATH_DEPTH` -> `TAURI_CLI_CONFIG_DEPTH`
- `TAURI_FIPS_COMPLIANT` -> `TAURI_BUNDLER_WIX_FIPS_COMPLIANT`
- `TAURI_DEV_WATCHER_IGNORE_FILE` -> `TAURI_CLI_WATCHER_IGNORE_FILENAME`
- `TAURI_TRAY` -> `TAURI_LINUX_AYATANA_APPINDICATOR`
- `TAURI_APPLE_DEVELOPMENT_TEAM` -> `APPLE_DEVELOPMENT_TEAM`
- `TAURI_PLATFORM` -> `TAURI_ENV_PLATFORM`
- `TAURI_ARCH` -> `TAURI_ENV_ARCH`
- `TAURI_FAMILY` -> `TAURI_ENV_FAMILY`
- `TAURI_PLATFORM_VERSION` -> `TAURI_ENV_PLATFORM_VERSION`
- `TAURI_PLATFORM_TYPE` -> `TAURI_ENV_PLATFORM_TYPE`
- `TAURI_DEBUG` -> `TAURI_ENV_DEBUG`

### Système d'événements

Le système d'événements a été repensé pour être plus simple à utiliser. Au lieu de s'appuyer sur la source de l'événement, il utilise maintenant une implémentation plus simple basée sur les cibles d'événements.

- La fonction `emit` émet maintenant l'événement vers tous les écouteurs.
- Ajout d'une nouvelle fonction `emit_to`/`emitTo` pour déclencher un événement vers une cible spécifique.
- `emit_filter` filtre maintenant selon [`EventTarget`](https://docs.rs/tauri/2.0.0/tauri/event/enum.EventTarget.html) au lieu d'une fenêtre.
- `listen_global` a été renommé en `listen_any`. Il écoute maintenant tous les événements, quels que soient leurs filtres et leurs cibles.
- JavaScript : `event.listen()` se comporte comme `listen_any`. Il écoute maintenant tous les événements, quels que soient leurs filtres et leurs cibles, sauf si une cible est définie dans les `Options`.
- JavaScript : `WebviewWindow.listen` et les API similaires n'écoutent que les événements émis vers leur `EventTarget` respectif.

### Prise en charge de plusieurs webviews

Tauri v2 introduit la prise en charge de plusieurs webviews, actuellement derrière le feature flag `unstable`.
Pour la prendre en charge, nous avons renommé le type Rust `Window` en `WebviewWindow` et la fonction `get_window` du Manager en `get_webview_window`.

Le type de l'API JS `WebviewWindow` est maintenant réexporté depuis `@tauri-apps/api/webviewWindow` au lieu de `@tauri-apps/api/window`.

### Nouvelle URL d'origine sous Windows

Sous Windows, les fichiers frontend des apps en production sont maintenant servis depuis `http://tauri.localhost` au lieu de `https://tauri.localhost`. À cause de cela, IndexedDB, LocalStorage et les cookies seront réinitialisés sauf si `dangerousUseHttpScheme` était utilisé en v1. Pour éviter cela, vous pouvez définir `app > windows > useHttpsScheme` sur `true` ou utiliser `WebviewWindowBuilder::use_https_scheme` pour continuer à utiliser le schéma `https`.

## Étapes de migration détaillées

Les scénarios communs que vous pouvez rencontrer lors de votre migration de Tauri 1.0 vers Tauri 2.0.

<a id="migrate-to-core-module"></a>

### Migrer vers le module Core

Le module `@tauri-apps/api/tauri` a été renommé en `@tauri-apps/api/core`.
Renommez simplement l'import du module :

```diff
- import { invoke } from "@tauri-apps/api/tauri"
+ import { invoke } from "@tauri-apps/api/core"
```

### Migrer vers un "CLI Plugin"

Les APIs Rust `App::get_cli_matches` et JavaScript `@tauri-apps/api/cli` APIs ont été retirées. Utilisez le plugin `@tauri-apps/plugin-cli` à la place:

1. Ajoutez vos dépendances Cargo:

```toml
# Cargo.toml
[dependencies]
tauri-plugin-cli = "2"
```

2. Utilisez-les dans un projet JavaScript ou Rust:

<Tabs syncKey="lang">
<TabItem label="JavaScript">

```rust
fn main() {
    tauri::Builder::default()
        .plugin(tauri_plugin_cli::init())
}
```

```json
// package.json
{
  "dependencies": {
    "@tauri-apps/plugin-cli": "^2.0.0"
  }
}
```

```javascript
import { getMatches } from '@tauri-apps/plugin-cli';
const matches = await getMatches();
```

</TabItem>
<TabItem label="Rust">

```rust
fn main() {
    use tauri_plugin_cli::CliExt;
    tauri::Builder::default()
        .plugin(tauri_plugin_cli::init())
        .setup(|app| {
            let cli_matches = app.cli().matches()?;
            Ok(())
        })
}
```

</TabItem>
</Tabs>

### Migrer vers un "Menu Module"

Les APIs Rust `Menu` ont été déplacées vers le module `tauri::menu` et remaniée pour utiliser la [crate muda](https://github.com/tauri-apps/muda).

#### Evenement du Menu

L'API Rust `tauri::Builder::on_menu_event` a été retirée. Utilisez `tauri::App::on_menu_event` ou `tauri::AppHandle::on_menu_event` à la place:

```rust
use tauri::menu::{CheckMenuItemBuilder, MenuBuilder, MenuItemBuilder};

tauri::Builder::default()
    .setup(|app| {
        let toggle = MenuItemBuilder::with_id("toggle", "Toggle").build(app)?;
        let check = CheckMenuItemBuilder::new("Mark").build(app)?;
        let menu = MenuBuilder::new(app).items(&[&toggle, &check]).build()?;

        app.set_menu(menu)?;

        app.on_menu_event(move |app, event| {
            if event.id() == check.id() {
                println!("`check` triggered, do something! is checked? {}", check.is_checked().unwrap());
            } else if event.id() == "toggle" {
                println!("toggle triggered!");
            }
        });
        Ok(())
    })
```

Notez qu'il y a deux manières de vérifier qu'un "item" de menu est sélectionné: on peut "move" (la fonctionnalités rust des closure) l'"item" vers un gestionnaire d'événement (event handler) sous forme de closure et comparer les IDs, ou définir une ID personnalisée via le constructeur `with_id` et utiliser cette ID (chaine de caractère) pour la comparer.

:::tip
Les "items" de menu peuvent être partagés entre les menus, et l'événement de menu est lié à un "item" de menu plutôt qu'à un menu ou une "window".
Si vous ne voulez pas que tous les écouteurs soient déclenchés lorsqu'un élément de menu est sélectionné, ne partagez pas les éléments de menu et utilisez plutôt des instances dédiées, que vous pouvez déplacer dans une closure passée à `tauri::WebviewWindow/WebviewWindowBuilder::on_menu_event`.
:::

#### Migrer vers un Menu

Utilisez `tauri::menu::Menu` à la place de `tauri::SystemTrayMenu`, `tauri::menu::Submenu` à la place de `tauri::SystemTraySubmenu` et `tauri::menu::PredefinedMenuItem` à la place de `tauri::SystemTrayMenuItem`. [Migration](#migrer-vers-un-menu)

#### Les événements de tray

`tauri::SystemTray::on_event` a été séparé en `tauri::tray::TrayIconBuilder::on_menu_event` et `tauri::tray::TrayIconBuilder::on_tray_icon_event` :

```rust
use tauri::{
    menu::{MenuBuilder, MenuItemBuilder},
    tray::{MouseButton, MouseButtonState, TrayIconBuilder, TrayIconEvent},
};

tauri::Builder::default()
    .setup(|app| {
        let toggle = MenuItemBuilder::with_id("toggle", "Toggle").build(app)?;
        let menu = MenuBuilder::new(app).items(&[&toggle]).build()?;
        let tray = TrayIconBuilder::new()
            .menu(&menu)
            .on_menu_event(move |app, event| match event.id().as_ref() {
                "toggle" => {
                    println!("toggle clicked");
                }
                _ => (),
            })
            .on_tray_icon_event(|tray, event| {
                if let TrayIconEvent::Click {
                        button: MouseButton::Left,
                        button_state: MouseButtonState::Up,
                        ..
                } = event
                {
                    let app = tray.app_handle();
                    if let Some(webview_window) = app.get_webview_window("main") {
                       let _ = webview_window.unminimize();
                       let _ = webview_window.show();
                       let _ = webview_window.set_focus();
                    }
                }
            })
            .build(app)?;

        Ok(())
    })
```

### Migrer vers la nouvelle API Window

Du côté Rust, `Window` a été renommé en `WebviewWindow`, son builder `WindowBuilder` s'appelle maintenant `WebviewWindowBuilder`, et `WindowUrl` s'appelle maintenant `WebviewUrl`.

De plus, la fonction `Manager::get_window` a été renommée en `get_webview_window`, et l'API `parent_window` de la fenêtre a été renommée en `parent_raw` pour prendre en charge une API de parent de fenêtre de plus haut niveau.

Du côté JavaScript, la classe `WebviewWindow` est maintenant exportée depuis le chemin `@tauri-apps/api/webviewWindow`.

La fonction `onMenuClicked` a été supprimée. Vous pouvez intercepter les événements de menu lors de la création d'un menu en JavaScript à la place.

### Migrer les binaires externes intégrés (sidecar)

<a id="migrate-permissions"></a>

### Migrer les permissions

L'allowlist v1 a été réécrite en un tout nouveau système de permissions qui fonctionne pour les plugins individuels et qui est beaucoup plus configurable pour la prise en charge multi-fenêtres et des URL distantes.
Ce nouveau système fonctionne comme une liste de contrôle d'accès (ACL), où vous pouvez autoriser ou refuser des commandes, attribuer des permissions à un ensemble spécifique de fenêtres et de domaines, et définir des portées d'accès.

Pour activer les permissions de votre app, vous devez créer des fichiers de capacités dans le dossier `src-tauri/capabilities`, et Tauri configurera automatiquement le reste.

La commande CLI `migrate` analyse automatiquement votre allowlist v1 et génère le fichier de capacité associé.

Pour en savoir plus sur les permissions et les capacités, consultez [la documentation de sécurité](/security/).
