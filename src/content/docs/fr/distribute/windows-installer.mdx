Les applications Tauri pour Windows sont distribuées soit comme Microsoft Installers (fichiers `.msi`) avec le [WiX Toolset v3],
soit comme exécutables d'installation (fichiers `-setup.exe`) avec [NSIS].

Notez que les installateurs `.msi` peuvent **uniquement être créés sur Windows**, car WiX ne fonctionne que sur les systèmes Windows.
La cross-compilation pour les installateurs NSIS est présentée ci-dessous.

Ce guide fournit des informations sur les options de personnalisation disponibles pour l'installateur.

## Build

Pour construire et empaqueter votre app dans un installateur Windows, vous pouvez utiliser la CLI Tauri et exécuter la commande `tauri build` sur un ordinateur Windows :

<CommandTabs
  npm="npm run tauri build"
  yarn="yarn tauri build"
  pnpm="pnpm tauri build"
  deno="deno task tauri build"
  bun="bun tauri build"
  cargo="cargo tauri build"
/>

:::note[Exigence VBSCRIPT pour les paquets MSI]

Construire des paquets MSI (`"targets": "msi"` ou `"targets": "all"` dans `tauri.conf.json`) nécessite l'activation de la fonctionnalité optionnelle VBSCRIPT sur Windows. Cette fonctionnalité est activée par défaut sur la plupart des installations Windows, mais si vous rencontrez des erreurs comme `failed to run light.exe`, vous devrez peut-être l'activer manuellement via **Settings** → **Apps** → **Optional features** → **More Windows features**. Consultez le [guide des prérequis](/fr/start/prerequisites/#vbscript-for-msi-installers) pour des instructions détaillées.

:::

### Construire des apps Windows sur Linux et macOS

La cross-compilation d'apps Windows depuis des hôtes Linux et macOS est possible avec des réserves lors de l'utilisation de [NSIS].
Ce n'est pas aussi direct que compiler directement sur Windows et c'est moins testé.
Elle ne doit donc être utilisée qu'en dernier recours si les VM locales ou des solutions CI comme GitHub Actions ne fonctionnent pas pour vous.

:::note

Signer des installateurs Windows cross-compilés nécessite un outil de signature externe.
Consultez la [documentation de signature] pour plus d'informations.

:::

Comme Tauri ne prend officiellement en charge que la cible Windows MSVC, la configuration est un peu plus impliquée.

#### Installer NSIS

<Tabs syncKey="OS">
<TabItem label="Linux">
Certaines distributions Linux proposent NSIS dans leurs dépôts. Par exemple, sur Ubuntu, vous pouvez installer NSIS avec cette commande :

```sh title=Ubuntu
sudo apt install nsis
```

Mais sur beaucoup d'autres distributions, vous devez compiler NSIS vous-même ou télécharger manuellement des Stubs et Plugins qui n'étaient pas inclus dans le paquet binaire de la distribution.
Fedora, par exemple, fournit uniquement le binaire, mais pas les Stubs et Plugins :

```sh title=Fedora
sudo dnf in mingw64-nsis
wget https://github.com/tauri-apps/binary-releases/releases/download/nsis-3/nsis-3.zip
unzip nsis-3.zip
sudo cp nsis-3.08/Stubs/* /usr/share/nsis/Stubs/
sudo cp -r nsis-3.08/Plugins/** /usr/share/nsis/Plugins/
```

</TabItem>

<TabItem label="macOS">
Sur macOS, vous aurez besoin de [Homebrew] pour installer NSIS :

```sh title=macOS
brew install nsis
```

</TabItem>
</Tabs>

#### Installer LLVM et le linker LLD

Comme le linker Microsoft par défaut ne fonctionne que sur Windows, nous devons aussi installer un nouveau linker.
Pour compiler le fichier Windows Resource utilisé notamment pour définir l'icône de l'app,
nous aurons aussi besoin du binaire `llvm-rc`, qui fait partie du projet LLVM.

<Tabs syncKey="OS">
<TabItem label="Linux">

```sh title="Ubuntu"
sudo apt install lld llvm
```

Sur Linux, vous devez aussi installer le paquet `clang` si vous avez ajouté des dépendances qui compilent des dépendances C/C++ dans leurs scripts de build.
Les apps Tauri par défaut ne devraient pas en avoir besoin.

</TabItem>
<TabItem label="macOS">
```sh title=macOS
brew install llvm
```

Sur macOS, vous devez aussi ajouter `/opt/homebrew/opt/llvm/bin` à votre `$PATH`, comme suggéré dans la sortie d'installation.

</TabItem>
</Tabs>

#### Installer la cible Rust Windows

En supposant que vous construisiez pour des systèmes Windows 64 bits :

```sh
rustup target add x86_64-pc-windows-msvc
```

#### Installer `cargo-xwin`

Au lieu de configurer les SDK Windows manuellement, nous utiliserons [`cargo-xwin`] comme « runner » de Tauri :

```sh
cargo install --locked cargo-xwin
```

Par défaut, `cargo-xwin` téléchargera les SDK Windows dans un dossier local au projet.
Si vous avez plusieurs projets et voulez partager ces fichiers, vous pouvez définir la variable d'environnement `XWIN_CACHE_DIR` avec le chemin de l'emplacement souhaité.

#### Construire l'app

Il suffit maintenant d'ajouter le runner et la cible à la commande `tauri build` :

<CommandTabs
  npm="npm run tauri build -- --runner cargo-xwin --target x86_64-pc-windows-msvc"
  yarn="yarn tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc"
  pnpm="pnpm tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc"
  deno="deno task tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc"
  bun="bun tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc"
  cargo="cargo tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc"
/>

La sortie de build se trouvera ensuite dans `target/x86_64-pc-windows-msvc/release/bundle/nsis/`.

### Construire pour 32 bits ou ARM

La CLI Tauri compile votre exécutable avec l'architecture de votre machine par défaut.
Si vous développez sur une machine 64 bits, la CLI produira donc des applications 64 bits.

Si vous devez prendre en charge des machines **32 bits**, vous pouvez compiler votre application avec une [cible Rust][platform support] **différente**
en utilisant le flag `--target` :

<CommandTabs
  npm="npm run tauri build -- --target i686-pc-windows-msvc"
  yarn="yarn tauri build --target i686-pc-windows-msvc"
  pnpm="pnpm tauri build --target i686-pc-windows-msvc"
  deno="deno task tauri build --target i686-pc-windows-msvc"
  bun="bun tauri build --target i686-pc-windows-msvc"
  cargo="cargo tauri build --target i686-pc-windows-msvc"
/>

Par défaut, Rust n'installe que les toolchains pour la cible de votre machine,
vous devez donc d'abord installer la toolchain Windows 32 bits : `rustup target add i686-pc-windows-msvc`.

Si vous devez construire pour **ARM64**, vous devez d'abord installer des outils de build supplémentaires.
Pour cela, ouvrez `Visual Studio Installer`, cliquez sur « Modify » puis, dans l'onglet « Individual Components », installez « C++ ARM64 build tools ».
Au moment de la rédaction, le nom exact dans VS2022 est `MSVC v143 - VS 2022 C++ ARM64 build tools (Latest)`.
Vous pouvez maintenant ajouter la cible Rust avec `rustup target add aarch64-pc-windows-msvc`, puis utiliser la méthode mentionnée ci-dessus pour compiler votre app :

<CommandTabs
  npm="npm run tauri build -- --target aarch64-pc-windows-msvc"
  yarn="yarn tauri build --target aarch64-pc-windows-msvc"
  pnpm="pnpm tauri build --target aarch64-pc-windows-msvc"
  deno="deno task tauri build --target aarch64-pc-windows-msvc"
  bun="bun tauri build --target aarch64-pc-windows-msvc"
  cargo="cargo tauri build --target aarch64-pc-windows-msvc"
/>

:::note

Notez que l'installateur NSIS lui-même restera x86 et s'exécutera sur la machine ARM via émulation. L'app elle-même sera un binaire ARM64 natif.

:::

## Prise en charge de Windows 7

Par défaut, le Microsoft Installer (`.msi`) ne fonctionne pas sur Windows 7, car il doit télécharger le bootstrapper WebView2 s'il n'est pas installé
(ce qui peut échouer si TLS 1.2 n'est pas activé dans le système d'exploitation). Tauri inclut une option pour intégrer le bootstrapper WebView2
(voir la section [Intégrer le bootstrapper WebView2](#embedded-bootstrapper) ci-dessous).
L'installateur basé sur NSIS (`-setup.exe`) prend aussi en charge le mode `downloadBootstrapper` sur Windows 7.

De plus, pour utiliser l'API Notification dans Windows 7, vous devez activer la fonctionnalité Cargo `windows7-compat` :

```toml title="Cargo.toml"
[dependencies]
tauri-plugin-notification = { version = "2.0.0", features = [ "windows7-compat" ] }
```

## Conformité FIPS

Si votre système exige que le bundle MSI soit conforme FIPS, vous pouvez définir la variable d'environnement `TAURI_BUNDLER_WIX_FIPS_COMPLIANT` à `true`
avant d'exécuter `tauri build`. Dans PowerShell, vous pouvez la définir pour la session de terminal courante comme ceci :

```powershell
$env:TAURI_BUNDLER_WIX_FIPS_COMPLIANT="true"
```

## Options d'installation WebView2

Les installateurs téléchargent par défaut le bootstrapper WebView2 et l'exécutent si le runtime n'est pas installé.
Vous pouvez aussi intégrer le bootstrapper, intégrer l'installateur hors ligne ou utiliser une version fixe du runtime WebView2.
Consultez le tableau suivant pour comparer ces méthodes :

| Méthode d'installation                             | Connexion Internet requise ? | Taille supplémentaire de l'installateur | Notes                                                                                                                               |
| :------------------------------------------------- | :--------------------------- | :-------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- |
| [`downloadBootstrapper`](#downloaded-bootstrapper) | Oui                          | 0 Mo                                    | `Default` <br /> Donne un installateur plus petit, mais n'est pas recommandé pour le déploiement Windows 7 via des fichiers `.msi`. |
| [`embedBootstrapper`](#embedded-bootstrapper)      | Oui                          | ~1,8 Mo                                 | Meilleure prise en charge de Windows 7 pour les installateurs `.msi`.                                                               |
| [`offlineInstaller`](#offline-installer)           | Non                          | ~127 Mo                                 | Intègre l'installateur WebView2. Recommandé pour les environnements hors ligne.                                                     |
| [`fixedVersion`](#fixed-version)                   | Non                          | ~180 Mo                                 | Intègre une version fixe de WebView2.                                                                                               |
| [`skip`](#skipping-installation)                   | Non                          | 0 Mo                                    | ⚠️ Non recommandé <br /> N'installe pas WebView2 dans le cadre de l'installateur Windows.                                           |

:::note

Sur Windows 10 (version April 2018 ou ultérieure) et Windows 11, le runtime WebView2 est distribué avec le système d'exploitation.

:::

### Downloaded Bootstrapper

C'est le paramètre par défaut lors de la construction de l'installateur Windows. Il télécharge le bootstrapper et l'exécute.
Il nécessite une connexion Internet mais produit un installateur plus petit.
Ce n'est pas recommandé si vous distribuez vers Windows 7 via des installateurs `.msi`.

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "webviewInstallMode": {
        "type": "downloadBootstrapper"
      }
    }
  }
}
```

### Embedded Bootstrapper

Pour intégrer le WebView2 Bootstrapper, définissez [webviewInstallMode] à `embedBootstrapper`.
Cela augmente la taille de l'installateur d'environ 1,8 Mo, mais améliore la compatibilité avec les systèmes Windows 7.

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "webviewInstallMode": {
        "type": "embedBootstrapper"
      }
    }
  }
}
```

### Offline Installer

Pour intégrer le WebView2 Bootstrapper, définissez [webviewInstallMode] à `offlineInstaller`.
Cela augmente la taille de l'installateur d'environ 127 Mo, mais permet d'installer votre application même sans connexion Internet.

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "webviewInstallMode": {
        "type": "offlineInstaller"
      }
    }
  }
}
```

### Fixed Version

Utiliser le runtime fourni par le système est excellent pour la sécurité, car les correctifs de vulnérabilités de la webview sont gérés par Windows.
Si vous voulez contrôler la distribution de WebView2 dans chacune de vos applications
(soit pour gérer les correctifs de release vous-même, soit pour distribuer des applications dans des environnements où une connexion Internet peut ne pas être disponible),
Tauri peut empaqueter les fichiers du runtime pour vous.

:::caution

Distribuer une version fixe du WebView2 Runtime augmente l'installateur Windows d'environ 180 Mo.

:::

1. Téléchargez le runtime WebView2 fixed version depuis le [site Microsoft][download-webview2-runtime].
   Dans cet exemple, le nom du fichier téléchargé est `Microsoft.WebView2.FixedVersionRuntime.128.0.2739.42.x64.cab`.
2. Extrayez le fichier dans le dossier core :

```powershell
Expand .\Microsoft.WebView2.FixedVersionRuntime.128.0.2739.42.x64.cab -F:* ./src-tauri
```

3. Configurez le chemin du runtime WebView2 dans `tauri.conf.json` :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "webviewInstallMode": {
        "type": "fixedRuntime",
        "path": "./Microsoft.WebView2.FixedVersionRuntime.98.0.1108.50.x64/"
      }
    }
  }
}
```

4. Exécutez `tauri build` pour produire l'installateur Windows avec le runtime WebView2 fixe.

### Ignorer l'installation

Vous pouvez supprimer de l'installateur la vérification de téléchargement du WebView2 Runtime en définissant [webviewInstallMode] à `skip`.
Votre application NE fonctionnera PAS si l'utilisateur n'a pas le runtime installé.

:::warning

Votre application NE fonctionnera PAS si l'utilisateur n'a pas le runtime installé et n'essaiera pas de l'installer.

:::

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "webviewInstallMode": {
        "type": "skip"
      }
    }
  }
}
```

## Version minimale de WebView2

Si votre app nécessite des fonctionnalités disponibles uniquement dans des versions plus récentes de WebView2 (comme les schémas d'URI personnalisés), vous pouvez demander à l'installateur Windows
de vérifier la version courante de WebView2 et d'exécuter le bootstrapper WebView2 si elle ne correspond pas à la version cible.

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "minimumWebview2Version": "110.0.1531.0"
    }
  }
}
```

## Personnaliser l'installateur WiX

Consultez la [configuration WiX] pour la liste complète des options de personnalisation.

### Template d'installateur

Le paquet Windows Installer `.msi` est construit avec le [WiX Toolset v3].
Actuellement, en plus des [configurations][configuration WiX] prédéfinies, vous pouvez le modifier en utilisant un code source WiX personnalisé
(un fichier XML avec une extension `.wxs`) ou avec des fragments WiX.

#### Remplacer le code de l'installateur par un fichier WiX personnalisé

Le XML Windows Installer défini par Tauri est configuré pour le cas d'utilisation courant
des applications simples basées sur webview (vous pouvez le trouver [ici][default wix template]).
Il utilise [handlebars] afin que la CLI Tauri puisse appliquer le branding de votre installateur selon la définition de votre `tauri.conf.json`.
Si vous avez besoin d'un installateur complètement différent, un fichier template personnalisé peut être configuré sur [`tauri.bundle.windows.wix.template`].

#### Étendre l'installateur avec des fragments WiX

Un [fragment WiX] est un conteneur où vous pouvez configurer presque tout ce que WiX propose.
Dans cet exemple, nous définissons un fragment qui écrit deux entrées de registre :

```xml
<?xml version="1.0" encoding="utf-8"?>
<Wix xmlns="http://schemas.microsoft.com/wix/2006/wi">
  <Fragment>
    <!-- these registry entries should be installed
		 to the target user's machine -->
    <DirectoryRef Id="TARGETDIR">
      <!-- groups together the registry entries to be installed -->
      <!-- Note the unique `Id` we provide here -->
      <Component Id="MyFragmentRegistryEntries" Guid="*">
        <!-- the registry key will be under
			 HKEY_CURRENT_USER\Software\MyCompany\MyApplicationName -->
        <!-- Tauri uses the second portion of the
			 bundle identifier as the `MyCompany` name
			 (e.g. `tauri-apps` in `com.tauri-apps.test`)  -->
        <RegistryKey
          Root="HKCU"
          Key="Software\MyCompany\MyApplicationName"
          Action="createAndRemoveOnUninstall"
        >
          <!-- values to persist on the registry -->
          <RegistryValue
            Type="integer"
            Name="SomeIntegerValue"
            Value="1"
            KeyPath="yes"
          />
          <RegistryValue Type="string" Value="Default Value" />
        </RegistryKey>
      </Component>
    </DirectoryRef>
  </Fragment>
</Wix>
```

Enregistrez le fichier fragment avec l'extension `.wxs` dans le dossier `src-tauri/windows/fragments` et référencez-le dans `tauri.conf.json` :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "wix": {
        "fragmentPaths": ["./windows/fragments/registry.wxs"],
        "componentRefs": ["MyFragmentRegistryEntries"]
      }
    }
  }
}
```

Notez que les ids des éléments `ComponentGroup`, `Component`, `FeatureGroup`, `Feature` et `Merge` doivent être référencés dans l'objet `wix`
de `tauri.conf.json`, respectivement dans `componentGroupRefs`, `componentRefs`, `featureGroupRefs`, `featureRefs` et `mergeRefs`,
pour être inclus dans l'installateur.

### Internationalisation

L'installateur WiX est construit avec la langue `en-US` par défaut.
L'internationalisation (i18n) peut être configurée avec la propriété [`tauri.bundle.windows.wix.language`],
qui définit les langues pour lesquelles Tauri doit construire un installateur.
Vous pouvez trouver les noms de langue à utiliser dans la colonne Language-Culture du [site Microsoft][localizing the error and actiontext tables].

#### Compiler un installateur WiX pour une seule langue

Pour créer un seul installateur ciblant une langue spécifique, définissez la valeur `language` comme chaîne :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "wix": {
        "language": "fr-FR"
      }
    }
  }
}
```

#### Compiler un installateur WiX pour chaque langue d'une liste

Pour compiler un installateur ciblant une liste de langues, utilisez un tableau.
Un installateur spécifique sera créé pour chaque langue, avec la clé de langue comme suffixe :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "wix": {
        "language": ["en-US", "pt-BR", "fr-FR"]
      }
    }
  }
}
```

#### Configurer les chaînes de l'installateur WiX pour chaque langue

Un objet de configuration peut être défini pour chaque langue afin de configurer les chaînes de localisation :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "wix": {
        "language": {
          "en-US": null,
          "pt-BR": {
            "localePath": "./wix/locales/pt-BR.wxl"
          }
        }
      }
    }
  }
}
```

La propriété `localePath` définit le chemin vers un fichier de langue, un XML configurant la culture de langue :

```xml
<WixLocalization
  Culture="en-US"
  xmlns="http://schemas.microsoft.com/wix/2006/localization"
>
  <String Id="LaunchApp"> Launch MyApplicationName </String>
  <String Id="DowngradeErrorMessage">
    A newer version of MyApplicationName is already installed.
  </String>
  <String Id="PathEnvVarFeature">
    Add the install location of the MyApplicationName executable to
    the PATH system environment variable. This allows the
    MyApplicationName executable to be called from any location.
  </String>
  <String Id="InstallAppFeature">
    Installs MyApplicationName.
  </String>
</WixLocalization>
```

:::note

Le champ `Culture` de l'élément `WixLocalization` doit correspondre à la langue configurée.

:::

Actuellement, Tauri référence les chaînes de locale suivantes : `LaunchApp`, `DowngradeErrorMessage`, `PathEnvVarFeature` et `InstallAppFeature`.
Vous pouvez définir vos propres chaînes et les référencer dans votre template ou vos fragments personnalisés avec `"!(loc.TheStringId)"`.
Consultez la [documentation de localisation WiX] pour plus d'informations.

## Personnaliser l'installateur NSIS

Consultez la [configuration NSIS] pour la liste complète des options de personnalisation.

### Template d'installateur

Le script `.nsi` de l'installateur NSIS défini par Tauri est configuré pour le cas d'utilisation courant
des applications simples basées sur webview (vous pouvez le trouver [ici][default nsis template]).
Il utilise [handlebars] afin que la CLI Tauri puisse appliquer le branding de votre installateur selon la définition de votre `tauri.conf.json`.
Si vous avez besoin d'un installateur complètement différent, un fichier template personnalisé peut être configuré sur [`tauri.bundle.windows.nsis.template`].

### Étendre l'installateur

Si vous devez seulement étendre certaines étapes d'installation, vous pourrez peut-être utiliser des hooks d'installateur au lieu de remplacer tout le template d'installateur.

Les hooks pris en charge sont :

- `NSIS_HOOK_PREINSTALL` : s'exécute avant la copie des fichiers, la définition des valeurs de clés de registre et la création des raccourcis.
- `NSIS_HOOK_POSTINSTALL` : s'exécute après que l'installateur a fini de copier tous les fichiers, de définir les clés de registre et de créer les raccourcis.
- `NSIS_HOOK_PREUNINSTALL` : s'exécute avant la suppression des fichiers, clés de registre et raccourcis.
- `NSIS_HOOK_POSTUNINSTALL` : s'exécute après la suppression des fichiers, clés de registre et raccourcis.

Par exemple, créez un fichier `hooks.nsh` dans le dossier `src-tauri/windows` et définissez les hooks dont vous avez besoin :

```nsh
!macro NSIS_HOOK_PREINSTALL
  MessageBox MB_OK "PreInstall"
!macroend

!macro NSIS_HOOK_POSTINSTALL
  MessageBox MB_OK "PostInstall"
!macroend

!macro NSIS_HOOK_PREUNINSTALL
  MessageBox MB_OK "PreUnInstall"
!macroend

!macro NSIS_HOOK_POSTUNINSTALL
  MessageBox MB_OK "PostUninstall"
!macroend
```

Vous devez ensuite configurer Tauri pour utiliser ce fichier de hooks :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "nsis": {
        "installerHooks": "./windows/hooks.nsh"
      }
    }
  }
}
```

#### Inclure des fichiers à côté du hook

Tauri inclut votre fichier de hooks depuis son script NSIS généré avec `!include`. Au niveau supérieur du fichier de hooks, `${__FILEDIR__}` fait référence au répertoire du fichier de hooks, vous pouvez donc inclure directement un fichier placé à côté.

Les corps de macros, en revanche, sont développés à l'endroit où Tauri les insère dans le script généré. Dans une macro de hook, `${__FILEDIR__}` fait donc référence au répertoire du script généré. Si une macro a besoin d'un fichier placé à côté du hook, capturez d'abord le répertoire du hook dans un `!define` de niveau supérieur :

```nsh
!include "${__FILEDIR__}\adjacent.nsh"
!define HOOK_FILE_DIR "${__FILEDIR__}"

!macro NSIS_HOOK_PREINSTALL
  File "${HOOK_FILE_DIR}\example.txt"
!macroend
```

#### Installer des dépendances avec des hooks

Vous pouvez utiliser des hooks d'installateur pour installer automatiquement les dépendances système requises par votre application. C'est particulièrement utile pour les dépendances d'exécution comme Visual C++ Redistributables, DirectX, OpenSSL ou d'autres bibliothèques système qui peuvent ne pas être présentes sur tous les systèmes Windows.

**Exemple d'installateur MSI (Visual C++ Redistributable) :**

```nsh
!macro NSIS_HOOK_POSTINSTALL
  ; Check if Visual C++ 2019 Redistributable is installed (via Windows Registry)
  ReadRegDWord $0 HKLM "SOFTWARE\Microsoft\VisualStudio\14.0\VC\Runtimes\x64" "Installed"

  ${If} $0 == 1
    DetailPrint "Visual C++ Redistributable already installed"
    Goto vcredist_done
  ${EndIf}

  ; Install from bundled MSI if not installed
  ${If} ${FileExists} "$INSTDIR\resources\vc_redist.x64.msi"
    DetailPrint "Installing Visual C++ Redistributable..."
    ; Copy to TEMP folder and then execute installer
    CopyFiles "$INSTDIR\resources\vc_redist.x64.msi" "$TEMP\vc_redist.x64.msi"
    ExecWait 'msiexec /i "$TEMP\vc_redist.x64.msi" /passive /norestart' $0

    ; Check wether installation process exited successfully (code 0) or not
    ${If} $0 == 0
      DetailPrint "Visual C++ Redistributable installed successfully"
    ${Else}
      MessageBox MB_ICONEXCLAMATION "Visual C++ installation failed. Some features may not work."
    ${EndIf}

    ; Clean up setup files from TEMP and your installed app
    Delete "$TEMP\vc_redist.x64.msi"
    Delete "$INSTDIR\resources\vc_redist.x64.msi"
  ${EndIf}

  vcredist_done:
!macroend
```

**Points clés :**

- Une bonne pratique consiste à toujours vérifier si la dépendance est déjà installée avec des clés de registre, l'existence d'un fichier ou la commande Windows [where].
- Utilisez les flags `/passive`, `/quiet` ou `/silent` pour éviter d'interrompre le flux d'installation. Consultez les options [msiexec] pour les fichiers `.msi`, ou le manuel de setup pour les flags propres à l'app.
- Incluez `/norestart` pour empêcher les redémarrages système automatiques pendant l'installation pour les setups qui redémarrent les appareils des utilisateurs.
- Nettoyez les fichiers temporaires et les installateurs empaquetés pour éviter d'alourdir l'application.
- Tenez compte du fait que les dépendances peuvent être partagées avec d'autres applications lors de la désinstallation.
- Fournissez des messages d'erreur utiles si l'installation échoue.

Assurez-vous d'empaqueter les installateurs de dépendances dans votre dossier `src-tauri/resources` et de les ajouter à `tauri.conf.json` afin qu'ils soient inclus et accessibles pendant l'installation depuis `$INSTDIR\resources\` :

```json title="tauri.conf.json"
{
  "bundle": {
    "resources": [
      "resources/my-dependency.exe",
      "resources/another-one.msi
    ]
  }
}
```

### Modes d'installation

Par défaut, l'installateur installe votre application uniquement pour l'utilisateur courant.
L'avantage de cette option est que l'installateur n'a pas besoin de privilèges administrateur pour s'exécuter,
mais l'app est installée dans le dossier `%LOCALAPPDATA%` au lieu de `C:/Program Files`.

Si vous préférez que l'installation de votre app soit disponible pour tout le système (ce qui nécessite des privilèges administrateur),
vous pouvez définir [installMode] à `perMachine` :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "nsis": {
        "installMode": "perMachine"
      }
    }
  }
}
```

Vous pouvez aussi laisser l'utilisateur choisir si l'app doit être installée uniquement pour l'utilisateur courant ou pour tout le système
en définissant [installMode] à `both`.
Notez que l'installateur exigera des privilèges administrateur pour s'exécuter.

Consultez [NSISInstallerMode] pour plus d'informations.

### Internationalisation

L'installateur NSIS est un installateur multilingue, ce qui signifie que vous avez toujours un seul installateur contenant toutes les traductions sélectionnées.

Vous pouvez spécifier les langues à inclure avec la propriété [`tauri.bundle.windows.nsis.languages`](/reference/config/#languages).
Une liste des langues prises en charge par NSIS est disponible dans [le projet GitHub NSIS].
Quelques [traductions propres à Tauri] sont requises ; si vous voyez des textes non traduits, n'hésitez pas à ouvrir une feature request dans [le dépôt principal de Tauri].
Vous pouvez aussi fournir des [fichiers de traduction personnalisés](/reference/config/#customlanguagefiles).

Par défaut, la langue par défaut du système d'exploitation est utilisée pour déterminer la langue de l'installateur.
Vous pouvez aussi configurer l'installateur pour afficher un sélecteur de langue avant que le contenu de l'installateur soit rendu :

```json title="tauri.conf.json"
{
  "bundle": {
    "windows": {
      "nsis": {
        "displayLanguageSelector": true
      }
    }
  }
}
```
